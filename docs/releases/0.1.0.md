## Known limitations of 0.1.0

- Explicit-duration engine with a free Gamma shape: the mean-sojourn category is report-only in the
  recovery suite (weak identifiability at the sample sizes tested, see the validation guide).
- The first forecast step uses the last observed covariate row; the covariate that is known at the origin
  is not used yet.
- A pinned `data.cache.snapshot` cannot be combined with covariates (one id names one cache entry).
- Weekday calendar only for forecast dates (no holiday calendar).
- GPU tests have not been run (no GPU runner).
- The nightly benchmark gate compares against a baseline recorded on the GitHub runner image; a runner image
  change can move it and require re-recording (`scripts/make_benchmark_baseline.py`).
- The real-data run is a manual `-m live` test, not a CI job.

## Cutting the release

1. `uv run towncrier build --version 0.1.0` collects `changelog.d/` into `CHANGELOG.md` (check with
   `--draft` first), and bump `version` in `pyproject.toml` from `0.1.0.dev0` to `0.1.0`.
2. Commit with a conventional message and push to `main`; wait for the PR workflow to pass on that commit.
3. `git tag v0.1.0` and push the tag. The `.github/workflows/release.yml` workflow checks that the tag
   equals `project.version`, builds the sdist and wheel and attaches them to a GitHub Release; publishing to
   PyPI is a manual, opt-in step of that workflow.

`[tool.semantic_release]` in `pyproject.toml` (conventional commits, `v{version}` tags, `0.y.z`) is configured
for later releases (`semantic-release --noop version --print` reports `0.1.0`); 0.1.0 is cut by the manual
steps above.
